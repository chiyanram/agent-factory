# Scripts

The orchestrator decides; the commands act. Each takes one command and prints one line. On GitLab, a PR is a merge
request, and `!12` stands for `#12`.

| script | does |
|---|---|
| `agent-factory init [<project>] [--repo <path>] [--yes]` | the guided setup of this laptop and one project ([Set up with agent-factory init](../how-to/set-up-with-init.md#set-up-with-agent-factory-init)): reads the clone, asks one round, writes `user.json` and the project file, pins the plugins, checks each piece and prints the next commands. A human runs it; the coordinator's settings deny it (#369) |
| `agent-factory poll [<project>]` | one line per open PR: head, draft, claimed, pipeline, `needs_human`, `stop`, open asks, `conflict` (`yes`, `no`, or `unknown` while the git host has not checked); plus each merged PR that still carries the claim; `--json` prints the records |
| `agent-factory claim [<project>] <pr>` / `agent-factory release [<project>] <pr>` | adds or removes the claim label; `claim` refuses a PR already claimed or not open; `release` of a PR with no claim says so and is not an error |
| `agent-factory review <project> <pr>` | one review round on a claimed PR: the context pack; the same patch-id as the last round reuses its verdict with no model run (with Act on still open, `needs-human`); after 3 rounds it refuses; then one finder run per lens the blast radius picks (`review.lenses`; the lane's lens count; every lens on the logic model for a one-way door; the test-integrity lens when an existing test changed), in parallel, their findings merged by `file:line` and rule, and one verify pass per kind, each a fresh read-only `claude -p` in a throwaway folder with the pack and the code at the head and no rule file; one thread per Act on and Consider; the status list; one summary note, last. It refuses a PR that already has a live implementer or review run, and a machine at `FACTORY_MAX_RUNS`, and holds `.claude/runs/reviewer-<pr>.pid` while it runs. A change that touches a file whose name holds a control character is refused, for a person to review. Exit 0 posted, reused or nothing to do, 3 when the head moved (nothing posted), 1 otherwise. Each pass's answer is kept under `.claude/runs/<pr>/<head>/`, with each lens's unique verified findings |
| (context pack) | built by `review`, one per head, under `$FACTORY_REPO/.claude/packs/`: rules from the default branch only; an unresolved rule pointer or link stops it. The intent and acceptance criteria come from the approved spec of the ticket the PR's `factory/<ticket>` branch names, read from `<home>/specs/<project>/` and checked against `<home>/approvals/<project>/`; the design from that spec's `## Design` link, as the default branch holds it. A spec edited after approval, or never approved, is named in the pack for the review to report; no spec in the store stops it. The PR description is data in the pack, never the contract |
| `agent-factory status [<project>] <pr> <sha> "<line>"` | posts one `[coordinator]` note through the posting template; refuses when the head is no longer `<sha>`, and a line that is not one line of text. The line it prints starts with "orchestrator last ran N min ago", flagged `LATE` after 3 poll intervals while any change is claimed (#103) |
| `agent-factory ask -- [<project>] <pr> <sha> "<question>"` | posts one `[writer] OPEN:` note; refuses when the head is no longer `<sha>`. `--` keeps a question that starts with `-` a question. The implementer does not run it: it writes its question to `report.json`, and the host posts it |
| `agent-factory spec <project> <ticket>` | checks a ticket's spec against the template: the local one (`$FACTORY_HOME/specs/<project>/<ticket>/spec.md`, default `~/.factory`), or with `"specStore": "issue"` in the project file the body of git host issue `<ticket>`, read through the git host seam, where the ticket is the issue number (#381). It prints its hash and the design's (`design none` with no `design.md` beside it), or every missing part (intent, numbered acceptance criteria, design, lane); an issue's spec has no design file, so its design is `none`. An optional `## Planned files` lists the paths the change will touch, one per line, for the lane check before the build (#230); `--template <ticket>` prints an empty one. The hash ignores line endings and trailing spaces, and changes on any real edit ([review 3](https://github.com/chiyanram/agent-factory/issues/30#issuecomment-6682553870), #127) |
| `agent-factory start <project> <ticket> [--yes] [--no-loop]` | records a human's START in `$FACTORY_HOME/starts/<project>/<ticket>.json`: who, the front door (`via`) and when. It opens the ticket; in the tiny lane it also lets the build begin. When `factory/<ticket>` is already on the git host it asks first (exit 3), and `--yes` starts anyway. It starts the orchestrator loop in the background when none runs; `--no-loop` does not (#305). A human runs it; the coordinator's settings deny it (#227) |
| `agent-factory approve <project> <ticket> <spec hash> [<design hash>] [--no-loop]` | records the human's approval in `$FACTORY_HOME/approvals/<project>/<ticket>.json`: the spec's full hash, the design's (`none` when there is no `design.md` beside the spec), who, the front door and when. The hashes on the command line are the ones the human saw, as `agent-factory spec` printed them; a spec or design that no longer has exactly that hash is refused. With the issue store the hash is the issue body's, and the record stays on this machine. It starts the orchestrator loop in the background when none runs; `--no-loop` does not (#305). A human runs it; the coordinator's settings deny it ([review 3](https://github.com/chiyanram/agent-factory/issues/30#issuecomment-6682553870), #104, #227) |
| `agent-factory waive <project> <ticket> <head>` | records the human's waiver of the test checks in `$FACTORY_HOME/waivers/<project>/<ticket>.json`: `kind: "test-change"`, the full commit id of the head the hits were listed at, who, the front door and when. The ready check clears the test check hits at that head; on a later head it looks again only at the files changed since, so a cleared file is flagged again only if it changes again. A waiver given again replaces it. A human runs it; the coordinator's settings deny it (#231) |
| `agent-factory request <capability> --file <draft.json>` | asks for a `tracker.comment`, `tracker.create` or `notify` write on an approved ticket; the project's policy performs it at once (0), keeps it for `confirm` and prints that command (3), or refuses it (1) ([Writes](connectors.md#writes)) |
| `agent-factory confirm <id> '<text>'` | performs a kept write when the text is the one `request` printed; run it only through the harness `ask` prompt |
| `agent-factory approval <project> <ticket>` | whether work may start: `approved` (exit 0), `stale` when the spec changed after approval (3; with the issue store, an edit to the issue's body), `missing` (4), or a broken record or spec (1); `dispatch` reads the same record |
| `agent-factory dispatch <project> [--once] [--dry-run]` | the orchestrator loop over the project: a pass of the orchestrator's table, then the next while a ticket is in flight: at once after a pass that ran a step or wrote to the git host, else after `FACTORY_POLL_MINUTES`, and after it too when a step failed the same way twice in a row; the log names what it waits on (`in flight: 4 (waiting on CI); next pass in 5 min`, or `next pass now`) (#445); ending by itself when none is, or after a pass whose runs a cap or a step not set up held back (see Triggers); `--once` is one pass, and `--dry-run` one pass that acts on nothing; exit 0, 1 when it cannot run (another loop runs, or 3 passes in a row failed), 2 when an action failed. An implementer run that ends blocked or asked logs `<ticket>: writer blocked: <why>` (or `writer asked:`) in place of `done`, even before its PR exists, and its `writer-ended` record in `$FACTORY_HOME/runs/<project>/<ticket>.jsonl` keeps `why`; a run the host blocked (a non-zero exit, no or a malformed report, a timeout, a stall) also keeps its output's last 40 lines, tokens scrubbed, in `runs/<project>/<ticket>/writer-<time>.log`, named as `output` (#62). `start` runs the loop in the background: read these lines in its `loop.log` |
| `agent-factory usage [<project>]` | what the orchestrator's runs spent, from the run records: today, the current window (the last `FACTORY_WINDOW_HOURS`) and this month, in dollars and tokens, for all, each project and each ticket, each split by run kind in its `kind` column (design-reviewer, test-first, implementer, cleanup, finder, verify pass, onboarder; a ticket's finders per lens; a review round recorded before its spend was split per run shows as `automated review`) (#337). Days and months are UTC. `+N?` is N runs with no spend reported, not in the sums. A review or eval run by hand writes no run record, so it is not in it (#131). Then the automated review's acted-on rate this month, all and per project, per lens (the rule or logic finder), per category and per bucket: each full round keeps its Act on and Consider findings at `.claude/runs/<change>/<head>/findings.json`, and the next full round counts one acted on when `git diff -U0` from that head changed a line of its file within 5 lines of it; no model decides it. A merge of the default branch into the branch can count too, so the rate is an upper bound (#220, ADR-0015 R4) |
| `agent-factory block [<project>] <pr> "<reason>" [<log>]` | labels `needs-human`, posts one `[coordinator] blocked: <reason>` note with the log as a field, then releases the claim; the label goes first |
| `agent-factory lint-edit '<command>'` | the implementer's hook, not yours: lints each file an Edit or Write changed and shows the implementer what failed. The command runs with no shell; one that needs a shell is reported to you and holds no implementer run |
| `agent-factory reconcile [<project>]` | removes each claim and run worktree with no live run, and each claim left on a merged PR; a live-run list it cannot read releases nothing. It never removes an implementer's worktree that holds unlanded work (#189): commits no remote branch holds, after a fetch, or uncommitted files. For an open PR it labels `needs-human` before any claim is released, pushes the commits on top of the PR's branch through the host push, with a blocked run's guards (fast-forward only, no `.factory`, no CI file), and posts one note naming the commits, the push and every uncommitted file, which it never commits. It tells you once for what the worktree holds, until that changes. A merged or closed PR gets no label and no push. A folder that is not one of the clone's worktrees, or a worktree it cannot fetch for, is kept and labels nothing. An automated review's worktree is removed as before. `FACTORY_DRY_RUN=1` fetches nothing and says which it would keep |

`poll`, `claim`, `release`, `status`, `ask`, `block` and `reconcile` act on the project they name first, else on the
one the coordinator's session was started for (`agent-factory coordinator <project>` sets `FACTORY_DEFAULT_PROJECT`),
else on the only project in `$FACTORY_HOME/projects`; with several and none named they refuse and list them (#382).
Each reads the project's `gitHost`, `gitHostProject` and `clone` from its project file through the settings layers;
an exported `FACTORY_FORGE`, `FACTORY_PROJECT` or `FACTORY_REPO` still wins, and with `FACTORY_PROJECT` exported and no
project named, a command reads the variables alone, as before.

`poll` keeps no state, so a restart re-reads everything. It reads the git host through its CLI (`gh api`, `glab api`),
pages every list to its end, and waits out a short rate limit; a longer one fails with the time it lasts until. It does not read approvals: an approval is the local
`agent-factory approve`. A note is the factory's only when it comes from the factory's login **and** starts with a
role prefix (`src/core/notes.ts`, #128); every other note is a person's. `asks` counts each `[coordinator] OPEN:` or
`[writer] OPEN:` note with no note after it from a project member: a GitLab Developer or more, or a GitHub
collaborator with write access. `stop` is the time of a maintainer's last note whose first line is exactly `/stop`
(a GitLab Maintainer or more, or a GitHub collaborator with write access), in UTC, or `undated` when its time does
not parse. A bot account is neither a member nor a maintainer, whatever its access, so a CI bot never answers an
ask or stops a change. `poll` reads the PR's conversation only: an answer or a `/stop` in a review comment or a review
body is not seen. `pipeline` is `success`, `failed`,
`running`, `canceled`, `skipped`, `manual`, `none`, or `unknown:<state>` for a state the git host sends that `poll` does
not know (#124); stand off an unknown one and tell the human. GitLab's own activity notes ("added ~label") are not
counted. A run is live while `claude agents --json` lists its Claude Code session (`writer-<pr>` or `reviewer-<pr>`).
